# Promoter Tracking System

## Overview

The Promoter Tracking System allows organizers to track sales generated by specific promoters using unique codes. This system is integrated with both the legacy Datafast payment flow and the new Stripe Connect implementation.

## Data Model

Promoter codes are tracked via the `promoter_code` column in the following tables:

1.  **`promoter_links`**: Defines the valid codes for an event.
    *   `event_id`: The event the code belongs to.
    *   `promoter_code`: The unique alphanumeric code (e.g., "SUMMER25").
    *   `promoter_name`: Optional name of the promoter.

2.  **`orders`**: Stores the code used for a completed purchase.
    *   `promoter_code`: The code used during checkout.
    *   `base_price_cents`: The revenue amount for the organizer (excluding fees).

3.  **`holds`**: Temporarily stores the code during the checkout process.
    *   `promoter_code`: Transferred to the order upon completion.

4.  **`rsvps`**: Tracks codes used for RSVP registrations.
    *   `promoter_code`: Captured during RSVP flow.

## Revenue Calculation

Accurate revenue tracking is critical for promoter commissions. The system handles two pricing models:

### 1. Stripe Guaranteed Net Model (Current)
*   **Source of Truth:** `orders.base_price_cents`
*   **Logic:** This field stores the exact amount the organizer receives, after all discounts and before fees are added.
*   **Calculation:** `Revenue = Sum(orders.base_price_cents)`
*   **Why:** Stripe fees are calculated on top of the base price. The `base_price_cents` is the "Net" amount guaranteed to the organizer.

### 2. Legacy Datafast Model (Historical)
*   **Source of Truth:** Extracted from `orders.total_amount_cents`
*   **Logic:** Legacy orders stored the total amount (Base + Fee + Tax). The base price must be mathematically extracted.
*   **Calculation:** Uses `extractBasePriceHistorical(total, date, fee_percentage)` to reverse-engineer the base price based on the fee structure active at the time of purchase (10% vs 7%).

## Implementation Details

### Dashboard Display
The Organizer Dashboard displays promoter statistics in two ways:
1.  **Server-Side Rendering (SSR):** `app/organizer/page.tsx` calculates initial stats using the logic above.
2.  **Client-Side Refresh:** `app/api/organizer/data/route.ts` provides real-time updates.

**Critical Note:** Both implementations MUST select `base_price_cents` from the `orders` table to ensure accurate revenue reporting for Stripe orders. Failure to do so causes the system to fall back to legacy extraction, which may incorrectly include fees in the revenue total.

### Checkout Flow
1.  User enters code on purchase page.
2.  Code is stored in `holds` table.
3.  Upon payment success:
    *   **Stripe:** `promoter_code` is retrieved from `holds` (or metadata) and saved to `orders`. `base_price_cents` is explicitly saved.
    *   **Datafast (Legacy):** `promoter_code` was saved to `orders`.

## Troubleshooting

### "Price Jumps" on Dashboard
If the dashboard shows the correct base price initially (e.g., $100) but then updates to a higher amount (e.g., $104.39) after a few seconds:
*   **Cause:** The client-side fetch (`/api/organizer/data`) is missing `base_price_cents` in its SQL query.
*   **Effect:** The frontend falls back to legacy extraction on the *total* amount (which includes fees), resulting in an inflated revenue figure.
*   **Fix:** Ensure `base_price_cents` is selected in the Supabase query in `app/api/organizer/data/route.ts`.
